## 用户场景与测试 *(必填)*

### 用户故事 1 - 查看当前工具列表与状态 (优先级: P1)

当用户打开浏览器插件的设置页面并进入"工具管理"模块时，用户可以看到当前所有可用工具的列表，每个工具显示名称、图标、简短描述和启用/禁用状态。用户可以一目了然地了解当前配置。

**优先级理由**: 这是工具管理功能的基础，用户必须能够查看当前工具配置才能进行后续的排序和启用/禁用操作。没有这个功能，其他功能无法实现。

**独立测试**: 可通过打开设置页面，检查工具列表是否正确显示所有工具（9个）及其状态，无需依赖其他功能。

**验收场景**:

1. **假设** 用户首次安装插件，**当** 用户打开设置页面的"工具管理"模块，**则** 显示所有 9 个工具（GitHub.dev、DeepWiki、CodeWiki、CodeSandbox、StackBlitz、nbviewer、gitdiagram、gitingest、githistory），并且所有工具默认处于启用状态
2. **假设** 用户已配置部分工具为禁用状态，**当** 用户打开设置页面，**则** 工具列表正确显示启用和禁用的工具状态（开关按钮状态与实际配置一致）
3. **假设** 用户查看工具列表，**当** 用户查看每个工具项，**则** 每个工具显示 16x16 图标、工具名称和一句简短描述（如 "GitHub 官方在线编辑器"）
4. **假设** 用户已自定义工具顺序，**当** 用户打开设置页面，**则** 工具列表按照用户自定义的顺序显示（而非默认的 order 1-9 顺序）

---

### 用户故事 2 - 通过拖拽调整工具顺序 (优先级: P1)

当用户需要将常用工具排在前面时，用户可以通过拖拽操作改变工具在列表中的顺序。拖拽完成后，新的顺序立即保存并同步到所有 Chrome 实例，下次打开工具菜单时工具将按照新顺序显示。

**优先级理由**: 这是核心功能之一，允许用户个性化工具顺序，将最常用的工具放在最上方以提高效率。这是用户最直接的需求。

**独立测试**: 可通过在设置页面拖拽工具，然后在 GitHub 页面打开工具菜单，验证顺序是否与设置页面一致。

**验收场景**:

1. **假设** 用户在工具列表中看到 GitHub.dev 排在第 1 位，**当** 用户将 GitHub.dev 拖拽到列表第 5 位，**则** GitHub.dev 移动到第 5 位，其他工具顺序相应调整
2. **假设** 用户完成拖拽操作，**当** 用户松开鼠标，**则** 新的工具顺序立即保存到 chrome.storage.sync（无需点击"保存"按钮）
3. **假设** 用户在设置页面调整了工具顺序，**当** 用户在 GitHub 页面打开工具下拉菜单，**则** 工具菜单中的工具按照新顺序显示（从上到下）
4. **假设** 用户在 Chrome 实例 A 调整了工具顺序，**当** 用户在同一账号的 Chrome 实例 B 打开设置页面，**则** 实例 B 显示与实例 A 相同的工具顺序（通过 chrome.storage.sync 同步）
5. **假设** 用户正在拖拽一个工具，**当** 用户将工具拖拽到列表边界之外，**则** 工具回到拖拽前的位置（拖拽取消）

---

### 用户故事 3 - 启用或禁用工具 (优先级: P1)

当用户不需要某些工具时，用户可以通过点击开关按钮禁用该工具。禁用后的工具不会在 GitHub 页面的工具下拉菜单中显示。用户可以随时重新启用已禁用的工具。

**优先级理由**: 这是核心功能之一，允许用户隐藏不常用的工具以简化菜单，提高常用工具的可见性和访问效率。

**独立测试**: 可通过在设置页面禁用工具，然后在 GitHub 页面打开工具菜单，验证被禁用的工具是否从菜单中消失。

**验收场景**:

1. **假设** 用户看到 CodeSandbox 工具处于启用状态，**当** 用户点击 CodeSandbox 的开关按钮，**则** 开关切换到禁用状态，CodeSandbox 工具标记为禁用
2. **假设** 用户禁用了 CodeSandbox，**当** 用户在 GitHub 页面打开工具下拉菜单，**则** 菜单中不显示 CodeSandbox 工具项
3. **假设** 用户禁用了部分工具，**当** 用户在设置页面点击某个已禁用工具的开关，**则** 该工具重新启用，并立即在工具菜单中显示
4. **假设** 用户禁用了 8 个工具，只保留 1 个工具启用，**当** 用户在 GitHub 页面打开工具菜单，**则** 菜单中只显示 1 个工具项
5. **假设** 用户尝试禁用最后一个启用的工具，**当** 用户点击该工具的开关按钮，**则** 系统阻止操作并显示提示 "至少需要保留一个工具启用"

---

### 用户故事 4 - 查看工具描述以识别用途 (优先级: P2)

当用户不确定某个工具的用途时，用户可以在设置页面查看每个工具的简短描述，帮助识别工具的主要功能和最佳使用场景。

**优先级理由**: 这是辅助功能，帮助用户了解工具用途，特别是对不熟悉这些第三方工具的新用户。但不影响核心的排序和启用/禁用功能。

**独立测试**: 可通过在设置页面查看每个工具的描述文本，验证描述是否准确且简洁。

**验收场景**:

1. **假设** 用户查看 GitHub.dev 工具，**当** 用户阅读其描述，**则** 显示 "GitHub's official online code editor for quick edits"
2. **假设** 用户查看 nbviewer 工具，**当** 用户阅读其描述，**则** 显示 "Render Jupyter notebooks with better viewing experience"
3. **假设** 用户查看 githistory 工具，**当** 用户阅读其描述，**则** 显示 "Visualize complete file modification history and evolution"
4. **假设** 用户查看所有工具，**当** 用户比较各工具描述，**则** 每个描述简洁明了（约40-60个字符），信息完整

---

### 用户故事 5 - 重置为默认配置 (优先级: P3)

当用户希望恢复插件的默认工具配置时，用户可以点击"重置为默认"按钮，将工具顺序恢复为默认顺序（order 1-9），并将所有工具恢复为启用状态。

**优先级理由**: 这是便利功能，在用户配置混乱或想重新开始时提供快捷恢复选项。但不是必需功能，优先级最低。

**独立测试**: 可通过先自定义配置（调整顺序、禁用部分工具），然后点击重置按钮，验证配置是否恢复为默认状态。

**验收场景**:

1. **假设** 用户已自定义工具顺序和启用/禁用状态，**当** 用户点击"重置为默认"按钮，**则** 系统显示确认对话框，提示 "确定要重置为默认配置吗？此操作不可撤销。"
2. **假设** 用户在确认对话框中点击"确定"，**当** 重置完成，**则** 工具列表恢复为默认顺序（GitHub.dev、DeepWiki、CodeWiki、CodeSandbox、StackBlitz、nbviewer、gitdiagram、gitingest、githistory），所有工具恢复为启用状态
3. **假设** 用户在确认对话框中点击"取消"，**当** 对话框关闭，**则** 工具配置保持不变（不执行重置操作）
4. **假设** 用户点击重置后，**当** 用户在 GitHub 页面打开工具菜单，**则** 工具菜单显示所有 9 个工具，按照默认顺序排列

### 边界情况

- 当用户在拖拽过程中意外刷新页面或关闭标签页时，拖拽操作应被取消，工具顺序保持为拖拽前的状态（已保存的状态）
- 当 chrome.storage.sync 配额已满时（每个扩展最多 100KB），系统应显示错误提示 "存储空间不足，无法保存配置"，并保持当前配置不变
- 当用户同时在多个 Chrome 实例中打开设置页面并进行配置时，最后保存的配置将覆盖之前的配置（符合 chrome.storage.sync 的 "最后写入优先" 行为）
- 当工具配置数据损坏或格式不正确时，系统应自动恢复为默认配置，并在设置页面显示警告提示 "配置数据异常，已恢复为默认设置"
- 当用户尝试禁用最后一个启用的工具时，系统应阻止操作并显示提示 "至少需要保留一个工具启用"
- 当新版本添加了新工具时，新工具应自动添加到用户配置的末尾，默认为启用状态（不覆盖用户已有的工具配置）
- 当工具描述包含特殊字符或 HTML 标签时，系统应正确转义以防止 XSS 攻击

## 需求定义 *(必填)*

### 功能需求

- **FR-001**: 系统必须在设置页面的"工具管理"模块中显示所有可用工具的列表，每个工具项包含 16x16 图标、工具名称、简短描述和启用/禁用开关
- **FR-002**: 系统必须支持用户通过拖拽操作调整工具在列表中的顺序，拖拽完成后立即保存新顺序到 chrome.storage.sync
- **FR-003**: 系统必须支持用户通过开关按钮启用或禁用工具，状态变化立即保存到 chrome.storage.sync
- **FR-004**: 系统必须在 GitHub 页面的工具下拉菜单中仅显示启用状态的工具，且工具顺序与设置页面中的自定义顺序一致
- **FR-005**: 系统必须在设置页面加载时从 chrome.storage.sync 读取用户的工具配置（顺序和启用/禁用状态），如果配置不存在则使用默认配置
- **FR-006**: 系统必须为每个工具提供一句简短的英文描述（约40-60个字符），帮助用户识别工具用途
- **FR-007**: 系统必须提供"重置为默认"按钮，点击后显示确认对话框，用户确认后将工具配置恢复为默认状态（默认顺序、所有工具启用）
- **FR-008**: 系统必须在重置操作完成后立即更新设置页面的工具列表显示，无需刷新页面
- **FR-009**: 系统必须通过 chrome.storage.sync 在用户的所有 Chrome 实例间同步工具配置
- **FR-010**: 系统必须在配置数据损坏或格式不正确时自动恢复为默认配置，并在设置页面显示警告提示
- **FR-011**: 系统必须阻止用户禁用最后一个启用的工具，当用户尝试禁用时显示提示 "至少需要保留一个工具启用"
- **FR-012**: 系统必须支持至少 9 个工具的排序和启用/禁用管理，并预留扩展性以支持未来新增工具
- **FR-013**: 系统必须在设置页面提供预览区域展示工具菜单效果，预览区域的工具链接应禁用点击（使用 `pointer-events: none`），仅供视觉预览

### 非功能需求

- **NFR-001**: 工具列表的拖拽操作必须流畅，拖拽响应延迟 ≤50ms（P95）
- **NFR-002**: 工具配置保存到 chrome.storage.sync 的操作必须在 500ms 内完成（P95）
- **NFR-003**: 设置页面的工具列表渲染必须在 200ms 内完成（P95，包含从 storage 读取配置的时间）
- **NFR-004**: 工具配置数据必须控制在 5KB 以内，以确保不超过 chrome.storage.sync 单个键值对的大小限制（8KB）
- **NFR-005**: 系统必须支持 Chrome 浏览器 90+ 版本（与插件的 minimum_chrome_version 一致）
- **NFR-006**: 设置页面的 UI 必须使用自定义 CSS 样式（BEM 命名规范 + `__github-switcher-` 前缀），保持与现有扩展一致的视觉风格
- **NFR-007**: 系统必须正确处理工具描述中的特殊字符（如 HTML 标签、引号），防止 XSS 攻击
- **NFR-008**: 拖拽操作必须提供视觉反馈（如拖拽时显示半透明的工具项副本、目标位置高亮等）
- **NFR-009**: 预览区域必须与实际工具菜单在视觉样式上保持一致（相同的图标、间距、hover 效果等），但禁用所有交互功能

### 关键实体

- **工具配置 (ToolConfiguration)**: 包含工具的顺序（order）和启用/禁用状态（enabled），存储在 chrome.storage.sync 中
- **工具项 (ToolItem)**: 在设置页面中展示的工具条目，包含图标、名称、描述、开关按钮和拖拽手柄
- **工具描述 (ToolDescription)**: 每个工具的简短文本描述，帮助用户识别工具用途
- **默认配置 (DefaultConfiguration)**: 系统预定义的工具顺序（order 1-9）和启用状态（所有工具启用），用于首次安装和重置操作

### 数据模型

详细的数据模型定义请参见 `data-model.md` 文档。核心实体包括：

- **UserPreferences**: 用户偏好设置（包含 openInNewTab, enabledTools, toolOrder 字段）
- **ToolEntry**: 工具静态配置（name, urlTemplate, order, iconPath）
- **ToolDescription**: 工具描述映射（TOOL_DESCRIPTIONS 常量）

工具描述常量（定义在 `src/lib/config.ts`）：

```typescript
const TOOL_DESCRIPTIONS: Record<number, string> = {
  1: 'GitHub\'s official online code editor for quick edits',
  2: 'AI-powered documentation generator for code repositories',
  3: 'Google\'s code visualization tool with interactive navigation',
  4: 'Online IDE with live preview for frontend projects',
  5: 'Quick launch development environment with framework templates',
  6: 'Render Jupyter notebooks with better viewing experience',
  7: 'Visualize Git repository branch relationships and history',
  8: 'Package entire codebase into single text file for sharing',
  9: 'Visualize complete file modification history and evolution',
};
```

## 成功标准 *(必填)*

### 可衡量结果

- **SC-001**: 用户在设置页面可在 200ms 内（P95）看到完整的工具列表及其当前配置状态
- **SC-002**: 用户完成拖拽操作后，新的工具顺序可在 500ms 内（P95）保存到 chrome.storage.sync
- **SC-003**: 用户切换工具的启用/禁用状态后，新状态可在 500ms 内（P95）保存到 chrome.storage.sync
- **SC-004**: 用户在设置页面调整工具顺序后，在 GitHub 页面打开工具菜单时，工具顺序与设置页面 100% 一致
- **SC-005**: 用户禁用工具后，在 GitHub 页面打开工具菜单时，被禁用的工具 100% 不显示
- **SC-006**: 用户点击重置按钮并确认后，工具配置可在 500ms 内（P95）恢复为默认状态
- **SC-007**: 系统对 100% 的工具描述正确显示，且英文描述长度控制在 40-60 个字符
- **SC-008**: 用户在 Chrome 实例 A 修改配置后，在同一账号的 Chrome 实例 B 可在 5 秒内（P95）看到同步后的配置（受 chrome.storage.sync 同步延迟影响）
- **SC-009**: 系统对 100% 的配置数据损坏情况能够自动恢复为默认配置，且在设置页面显示警告提示
- **SC-010**: 拖拽操作的响应延迟 ≤50ms（P95），用户体验流畅无卡顿
- **SC-011**: 系统对 100% 的尝试禁用最后一个工具的操作能够正确阻止并显示提示

### 数据流

```
用户操作流程（拖拽排序）:
1. 用户在 Options Page 拖拽工具 A 到新位置
2. DragAndDrop Handler 更新内存中的 toolOrder 数组
3. 调用 savePreferences(newPreferences) 保存到 chrome.storage.sync
4. UI 组件重新渲染工具列表（基于新的 toolOrder）
5. chrome.storage.sync 自动同步到其他 Chrome 实例
6. 用户在 GitHub 页面打开工具菜单时，Content Script 读取 toolOrder 并按顺序渲染工具

用户操作流程（启用/禁用工具）:
1. 用户在 Options Page 点击工具 B 的开关按钮
2. Toggle Handler 更新 enabledTools 数组（添加或移除工具 ID）
3. 调用 savePreferences(newPreferences) 保存到 chrome.storage.sync
4. UI 组件更新开关状态
5. 用户在 GitHub 页面打开工具菜单时，Content Script 读取 enabledTools 并过滤显示

用户操作流程（重置为默认）:
1. 用户在 Options Page 点击"重置为默认"按钮
2. 显示确认对话框
3. 用户点击"确定"
4. 调用 savePreferences(DEFAULT_PREFERENCES) 保存默认配置
5. UI 组件重新渲染工具列表（基于默认配置）
```

### 技术选型

- **UI 框架**: Native DOM + TypeScript（保持与现有项目一致，避免引入 React/Vue 等框架）
- **拖拽库**: SortableJS（轻量级拖拽库，8KB gzipped，经过充分测试，功能完善）
- **样式**: CSS Modules 或 BEM 命名规范，继续使用 `__github-switcher-` 前缀隔离样式
- **存储**: chrome.storage.sync（现有技术栈）
- **构建工具**: Plasmo 0.90.5（现有技术栈）
- **测试**: Vitest（现有技术栈），新增设置页面的 E2E 测试

### 性能考虑

- **拖拽性能**: 使用 `requestAnimationFrame` 优化拖拽过程中的 DOM 更新，避免卡顿
- **存储性能**: 使用防抖（debounce）技术，避免频繁保存到 chrome.storage.sync（例如拖拽过程中只在松开鼠标时保存一次）
- **渲染性能**: 工具列表采用虚拟滚动（如果未来工具数量超过 20 个）或直接渲染（9 个工具量级较小，直接渲染即可）
- **数据大小**: toolOrder 数组最多 9 个整数，enabledTools 数组最多 9 个整数，总数据量 <1KB，远低于 chrome.storage.sync 单个键值对 8KB 限制

## 风险与缓解措施 *(必填)*

### 技术风险

**R-001: 拖拽操作在某些浏览器或设备上性能不佳**
- 风险等级: 中
- 影响: 用户体验下降，拖拽卡顿
- 缓解措施: 
  - 使用 SortableJS 库，该库经过充分测试且性能优秀
  - 使用 `requestAnimationFrame` 优化 DOM 更新
  - 在低性能设备上进行测试，确保拖拽响应 ≤50ms

**R-002: chrome.storage.sync 同步延迟导致多实例配置不一致**
- 风险等级: 低
- 影响: 用户在一个 Chrome 实例修改配置后，在另一个实例看不到即时更新
- 缓解措施:
  - 在设置页面添加说明，告知用户同步可能需要 5-10 秒
  - 监听 chrome.storage.onChanged 事件，在配置变化时自动刷新 UI
  - 在工具菜单中也监听 chrome.storage.onChanged，动态更新菜单

**R-003: 配置数据损坏导致工具菜单无法正常显示**
- 风险等级: 低
- 影响: 用户工具菜单异常，无法使用插件核心功能
- 缓解措施:
  - 在读取配置时添加数据校验逻辑（例如检查 toolOrder 数组是否包含重复 ID、是否包含无效 ID）
  - 如果检测到数据异常，自动恢复为默认配置并显示警告提示
  - 在 Content Script 中也添加容错逻辑，确保即使配置异常也能降级显示默认工具菜单

### 用户体验风险

**R-004: 用户误操作导致重要工具被禁用**
- 风险等级: 中
- 影响: 用户可能误点击开关禁用常用工具，影响使用效率
- 缓解措施:
  - 在开关按钮旁添加明确的视觉提示（启用/禁用状态颜色区分）
  - 考虑添加"撤销"功能（使用 chrome.storage 的版本管理，或在内存中保留上一次配置）
  - 提供"重置为默认"按钮作为快捷恢复方式

**R-005: 拖拽操作不直观，用户不理解如何排序**
- 风险等级: 低
- 影响: 用户无法使用拖拽排序功能
- 缓解措施:
  - 在设置页面添加简短的使用说明或教程（例如 "拖拽工具可调整顺序"）
  - 在拖拽手柄上使用明确的图标（如 ⋮⋮ 或 ≡ 图标）
  - 提供拖拽时的视觉反馈（半透明副本、目标位置高亮）

### 兼容性风险

**R-006: 新字段 toolOrder 与旧版本插件不兼容**
- 风险等级: 低
- 影响: 用户从旧版本升级到新版本时，工具顺序异常
- 缓解措施:
  - 将 toolOrder 设计为可选字段，如果不存在则使用默认顺序（基于 TOOLS 数组的 order 字段）
  - 在首次加载时，如果检测到 toolOrder 不存在，自动生成默认的 toolOrder 并保存
  - 在 CHANGELOG 中记录数据迁移逻辑，确保可追溯

**R-007: 未来新增工具时，用户配置未包含新工具**
- 风险等级: 低
- 影响: 新工具不显示在用户的工具菜单中
- 缓解措施:
  - 在加载配置时，检查 TOOLS 数组是否包含 toolOrder 中未列出的新工具
  - 如果检测到新工具，自动添加到 toolOrder 末尾，并默认启用
  - 在设置页面显示提示 "检测到新工具，已自动添加到列表末尾"
